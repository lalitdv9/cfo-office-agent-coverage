## Summary
Undergraduate-team system paper describing a hybrid invoice-extraction platform: preprocessing (noise reduction, Hough-transform skew correction, binarization), cascaded OCR (Tesseract 5 default; DocTR/TrOCR; cloud OCR fallbacks), layout analysis (TableNet/CascadeTabNet, invoice-fine-tuned LayoutLM, graph relational models), Gemini-API LLM entity extraction/disambiguation, YOLOv5 field detection, BERT-NER, rule/regex fallbacks, arithmetic consistency validation, hash deduplication, audit trails, and JSON/CSV/Excel/DB + REST export to ERP (SAP, QuickBooks).

## Tasks
- Single task family: invoice field + line-item extraction (vendor info, invoice numbers, dates, item names, quantities, unit prices, tax, totals). No task counts, no named benchmark dataset. "Data sharing is not applicable for this study."

## Eval method
Under-specified: Results section reports aggregate claims with two figures (human-intervention reduction; processing-time comparison) but NO dataset size, ground-truth annotation protocol, metric definitions, or baselines beyond "manual/traditional OCR". Closest to unvalidated self-reported accuracy.

## Agent scope

## UNVERIFIED
- All performance claims (92-95% OCR accuracy, 80% intervention reduction, 95-97% end-to-end accuracy): no dataset, protocol, or per-field tables to substantiate; figures are images.
- Internal inconsistency: Methodology describes a rich multi-model architecture (YOLOv5, BERT-NER, TableNet, LayoutLM, GNN, cloud OCR cascade), while Algorithm 1 shows a minimal pipeline (PDFPlumber -> Tesseract fallback -> single Gemini call -> Excel), suggesting the described architecture may exceed the implemented/evaluated system.
- Venue/peer-review status unknown; citation list has anomalies (e.g., ref 22 "Generative Face Completion" cited for OCR; ref 24 LLaMA cited for the Gemini API).
